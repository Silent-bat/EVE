BriefOS

Version 1.0 — Final Draft → Ready to build Author: Rosnel Kana May 2026

Problem

OpenClaw/Moltbot proved that millions of people want an autonomous AI agent that manages their digital life — 145k+ GitHub stars in three weeks. But it failed on every front that matters for adoption: desktop-only, credentials stored in plaintext, $250+ to install, and no mobile presence. Nobody has answered this demand on mobile.

Meanwhile the conversation paradigm for AI is still reactive — you open an app, you type a question, you wait. A real personal agent should do the opposite: monitor your world and interrupt you when something needs your attention.

Solution

BriefOS is a mobile-first AI agent with two complementary modes. In its ambient mode, it monitors your Gmail and Google Calendar in the background and proactively contacts you when urgency crosses a threshold — like a colleague tapping you on the shoulder. In its conversational mode, you speak to it naturally, in real time, with voice conversations designed to feel like talking to a real person — complete with thinking sounds, natural pacing, and the ability to interrupt mid-sentence.

Anti-persona

Not for users who want full autonomous control — "do everything without asking me." That's OpenClaw's failed model and its fatal security flaw. BriefOS is designed for people who want a proactive AI partner with human approval always in the loop.

V2 — proactive ambient agent

The agent monitors continuously server-side every 15 minutes using a lightweight triage LLM. When urgency crosses a threshold, it proactively contacts the user — not waiting for 8am, but acting like a real assistant who interrupts when something matters. Combined with a Dynamic Island persistent presence on iOS and a floating bubble on Android.

V2 — voice conversations

Natural real-time voice conversations using WebRTC via LiveKit, voice synthesis via ElevenLabs Turbo (streaming, chunk by chunk), and VAD (Voice Activity Detection) via Silero running on-device for instant end-of-speech detection. The agent uses a carefully designed voice prompt to produce natural ticks, hesitations, and rhythm variation — not robotic, not uniform.

Stack decision — full picture

Mobile
React Native + Expo — cross-platform from day one. Expo managed workflow for push notifications, OTA updates, and store submissions. Native modules in Swift/Kotlin added in V2 for Dynamic Island and VAD.
Backend
Go + Fiber — goroutines handle thousands of concurrent WebSocket connections natively without Redis queue complexity for real-time flows. Binaire ~8MB, startup in ~50ms, predictable memory under load.
Realtime
WebSockets + LiveKit (V2) — WebSockets for text/briefing streaming in V1. LiveKit WebRTC infrastructure for audio in V2 — the same protocol used by Google Meet, optimized for low-latency audio transport.
Agent jobs
Asynq — Redis-backed job queue for Go. Handles scheduled briefing jobs, 15-minute triage polling, retries, and rate limiting against Google APIs. Equivalent to BullMQ but native Go.
LLM
Claude Haiku for triage + Claude Sonnet for briefing/drafts — two-speed strategy. Haiku costs ~$0.001 per triage call, Sonnet handles quality generation. Hard per-user daily budget of ≤$0.08 enforced at infra level.
Voice
ElevenLabs Turbo v2.5 + OpenAI Realtime API — ElevenLabs for a custom BriefOS voice with designed personality. OpenAI Realtime for voice-to-voice mode where lowest latency is priority. Streaming chunk-by-chunk in both cases.
Database
PostgreSQL + sqlc — sqlc generates type-safe Go code from raw SQL. Full query control, no ORM magic. Users, preferences, action history, audit log, conversation context.
Cache
Redis — dual role: Asynq job queue backend + cache for refreshed OAuth tokens and user preferences. Avoids database round-trips on every triage cycle.
Security
AES-256 at rest + secrets manager — OAuth tokens never stored in plaintext. Encrypted via AES-256, stored in AWS Secrets Manager or Vault. Direct response to OpenClaw's fatal flaw. Revocable at any time from the app.
Infra
Fly.io — edge deployment places servers geographically close to users. Critical for voice latency. Sub-100ms server round-trip from Douala/Lagos to nearest Fly.io region. Scales with fly scale count.
Analytics
PostHog + Sentry — PostHog for product analytics (briefing open rates, approval rates, D7/D30 retention). Sentry for error tracking. Both ship on day one — no blind flying.

Key architectural decision — server-side agent

The agent brain runs entirely on the server, not on the device. The mobile app is only the approval UI and the voice interface. This single decision solves the battery drain problem, the iOS background kill problem, and the "agent stops when you lock your phone" problem — all at once. The server polls Gmail every 15 minutes; the phone just receives push notifications and displays results.

Why voice is hard — the root problem

A TTS voice sounds robotic not because of audio quality, but because of uniform prosody. Human speech constantly varies rhythm, pace, and pitch. The brain detects the regularity of synthetic speech immediately and triggers an uncanny valley response. Fixing this requires acting on three dimensions simultaneously: pipeline latency, voice quality, and the linguistic patterns of the text being spoken.

Architecture — streaming pipeline

Rather than waiting for a complete LLM response before generating audio, BriefOS uses a three-goroutine streaming pipeline. The first goroutine receives tokens from Claude. The second buffers tokens until a natural sentence boundary is detected (typically 8–12 words). The third immediately sends each completed sentence to ElevenLabs for synthesis and streams the audio chunks to the client. The result: the user hears the first words within 400–600ms of finishing their sentence.

Barge-in — the most important naturalness feature

When the user speaks while the agent is talking, Silero VAD detects it on-device within milliseconds. The app immediately sends a stop signal via WebSocket, the server cancels the current synthesis stream, and processing begins on the new input. Without barge-in, users must wait politely — which feels deeply unnatural and breaks the conversational illusion entirely.

Voice personality design

The BriefOS voice is designed at three levels. The ElevenLabs voice model is configured with a specific emotional age, energy level, and personality — not the default "professional assistant" voice every competitor uses. The system prompt instructs Claude to produce text written for speech, not reading — using thinking sounds, natural connectors, and rhythm variation. SSML markup adds fine-grained control over pauses and emphasis where needed.

System prompt excerpt — voice mode

You are BriefOS, speaking aloud in a real conversation. Use natural speech patterns: thinking sounds like "Hmm..." or "Let me think...", connectors like "Actually," or "Here's the thing —", and vary your sentence rhythm. Never use markdown, bullet points, or symbols. Start responses with a brief acknowledgment before the substance. Pause naturally before complex answers.

V2 voice-to-voice mode

For users who prioritize minimum latency over voice customization, BriefOS V2 supports a voice-to-voice mode using OpenAI Realtime API. In this mode, audio travels directly to a multimodal model that understands tone and emotion in the user's voice — no transcription step. End-to-end latency drops to 200–400ms, within the range of natural human conversation.

6-week V1 sprint plan

The first two weeks are validation, not construction. Writing code before confirming cost model and willingness to pay is the most common mistake in this type of project.

Week 0 — Validate cost model
Build a script simulating one user's full daily usage — 20 emails read, 5 summaries generated, 3 reply drafts. Measure exact token cost. Hard gate: if cost exceeds $0.10/user/day, fix the model before writing any product code.
Week 1 — Validate willingness to pay
Figma mockup + 60-second demo video. Post in developer communities, DM your network. Goal: 10 people pay $9 upfront before a single line of product code is written. If this fails, the market signal is wrong — pivot before investing 6 weeks.
Week 2 — Backend foundation
Go + Fiber scaffold. Gmail + Calendar OAuth2 with encrypted token storage. Asynq scheduled briefing job. Claude Sonnet integration with hard per-user daily budget. Unit tests on email parsing and ranking logic.
Week 3 — Mobile app
React Native + Expo. Auth flow. Briefing screen UI. Swipe-to-approve interaction. Push notifications via Expo. WebSocket connection to backend for real-time token streaming.
Week 4 — Integration and billing
End-to-end flow working. Stripe subscription integration. TestFlight + Play Store internal testing. Bug fixes with 5 beta users from the Week 1 waitlist.
Week 5 — Launch
App store submissions. Landing page live. PostHog + Sentry instrumented. Launch to waitlist. Collect feedback aggressively — every user who churns gets a DM within 24 hours.

Risk register

Critical

Google OAuth verification wall

Reading real users' Gmail requires Google security review. Process takes 4–8 weeks and costs $15k–$75k for third-party audit. Mitigation: launch V1 with "bring your own Google OAuth credentials" — users create their own Google Cloud project. Constraining UX but avoids the wall entirely until you have revenue to pay for verification.

Critical

LLM cost overrun

If the daily per-user token cost exceeds $0.10, the business model breaks at every price point. Mitigation: validate in Week 0 before writing any product code. Hard budget cap enforced at infrastructure level — briefings truncate gracefully if the budget is hit.

High

Day-2 retention

If the first briefing is too generic, too long, or misranked, the user disables notifications and never returns. You have one chance per day to prove value. Mitigation: instrument every briefing from day one with PostHog. Interview every churned user within 24 hours. The quality of the urgency ranking model is the product.

High

Voice latency on mobile networks

LiveKit WebRTC works well on WiFi. On 3G/4G in Africa and Southeast Asia, jitter and packet loss can degrade real-time audio. Mitigation: test on real mobile networks early. Implement adaptive bitrate and a graceful fallback to text mode when audio quality drops below threshold.

Medium

Cold start personalization paradox

The first briefing will be generic — no data on user priorities yet. But the first briefing determines whether they stay. Mitigation: onboarding quiz asking the user to identify their 3 most important email senders and topics. Uses this as a prior for the first week of briefings.

Low

Big tech competitor

Google, Apple, and Microsoft all see the same gap. They will ship something eventually. Mitigation: speed, brand trust, and owning the mobile-first African/LatAm/SEA market before they notice it exists. By the time a Google product ships globally, BriefOS can be the default for 2 billion underserved mobile users.
